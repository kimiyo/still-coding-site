[CollaBoard](https://collaboard.still-coding.cc/)는 서버에 팀의 자료를 저장하지 않는 협업 앱입니다. 그 구조는 [이전 글](/notes/collaboard-webrtc-p2p-room/)에서 다뤘습니다. 이 글은 그다음 이야기입니다. 앱이 어느 정도 만들어진 뒤, **내 코드를 공격자의 눈으로 다시 읽었을 때** 무엇이 나왔는가입니다.

2026년 9월 14일에 `worker/`, `frontend/`, `test/` 전체(약 12,790줄)를 점검했고, 테스트는 모두 통과하고 있었습니다. 그런데도 심각한 구멍이 세 개 나왔습니다. 테스트가 통과한다는 것은 **테스트가 다루는 것이 문제없다**는 뜻일 뿐이었습니다.

## 1. 발견한 세 가지 구멍

### 1) 비밀번호 검사가 WebSocket에서 빠져 있었다

방에 비밀번호가 있으면 `/join` 요청에서 비밀번호를 확인합니다. 그런데 실제 참여는 그다음에 여는 **WebSocket 연결**로 이루어지고, 그 연결(`/rooms/:id/ws`)은 방이 있는지와 `sessionId` 형식만 검사했습니다. 방 코드만 알면 비밀번호 없이 들어와서 참가자 목록과 통신 내용을 받을 수 있었습니다. 비밀번호 해시는 SHA-256 한 번이었고, 틀린 횟수 제한도 없었습니다.

### 2) 방장 권한을 가로챌 수 있었다

- 서버가 `hostSessionId`를 모든 참가자에게 알려 주고 있었습니다.
- 그런데 `sessionId`가 방장의 것과 같으면 **토큰 없이도 방장**으로 취급했습니다.
- 방장 승계 기준인 `joinedAt`을 클라이언트가 쿼리 문자열로 보냈습니다.
- 방장이 없을 때는 누구나 `claim-host`로 방장을 요청할 수 있었습니다.

공개된 방장의 `sessionId`로 접속하기만 하면 방장이 되어 앱을 바꾸고, 사람을 내보내고, 방장을 넘길 수 있었습니다.

### 3) 강퇴가 연결을 끊지 않았다

`kick`은 대상에게 "강퇴되었다"는 메시지를 보내고 나머지에게 "나갔다"고 알릴 뿐이었습니다. **소켓을 닫지 않았고, 재입장도 막지 않았습니다.** 강퇴된 사람은 계속 데이터를 받았고, 새로고침만 하면 다시 들어왔습니다.

## 2. 세 구멍의 공통점: sessionId를 비밀처럼 다뤘다

세 구멍에는 공통된 뿌리가 있습니다. `sessionId`는 WebRTC 연결을 맺을 때 참가자끼리 서로를 지목하는 데 쓰여서 **모두에게 알려질 수밖에 없는 값**입니다. 그런데 코드는 이 값을 "이 사람이 누구인가"를 증명하는 데 썼습니다. 이름표를 신분증으로 쓴 셈입니다.

그래서 고치는 원칙을 이렇게 세웠습니다(수정 계획서 0.3절).

> **서버가 권한의 유일한 판단자.** 클라이언트가 보낸 `role`, `joinedAt`, `senderId`는 참고값일 뿐 신뢰하지 않는다.
> **sessionId는 공개 식별자.** 숨길 수 없으니, sessionId만으로는 아무 권한도 얻지 못하게 한다.

## 3. 이렇게 고쳤다

### 입장권(wsTicket): WebSocket의 문을 잠그다

비밀번호 확인(또는 방장 승인)을 통과하면 서버가 **60초 동안, 한 번만 쓸 수 있는 입장권**을 발급합니다. WebSocket은 이 입장권 없이는 열리지 않습니다.

```js
// worker/room.js — WebSocket 연결 시
const ticketId = url.searchParams.get("ticket") || "";
const ticketKey = `ticket:${ticketId}`;
const ticket = ticketId ? await this.ctx.storage.get(ticketKey) : null;
if (ticket) await this.ctx.storage.delete(ticketKey);   // 일회용
if (!validateTicket(ticket, { sessionId }).ok) {
  return text("invalid_ticket", 401);
}
if (await this.ctx.storage.get(`ban:${sessionId}`)) {
  return text("banned", 403);
}
```

입장권은 쓰는 즉시 지워지고(재사용 불가), 60초가 지나면 만료됩니다. 비밀번호도 SHA-256 한 번에서 **PBKDF2(반복 100,000회)**로 바꾸고, 같은 곳에서 5번 틀리면 429로 막습니다. (Workers 런타임이 허용하는 최대 반복 횟수가 100,000이라는 주석이 코드에 있습니다.)

### 멤버 토큰: sessionId의 주인임을 증명하다

새로고침하거나 브라우저를 껐다 켜도 같은 방에 돌아오려면 "이 sessionId의 주인이 나"라는 증명이 필요합니다. 그래서 첫 입장 때 **멤버 토큰**을 발급하고, 서버에는 원문이 아니라 **SHA-256 해시만** 저장합니다. 클라이언트는 토큰을 브라우저(`localStorage`)에 방별로 보관합니다.

`sessionId`와 `memberToken`의 역할이 갈립니다.

| | sessionId | memberToken |
| --- | --- | --- |
| 성격 | 공개 식별자 | 비밀 |
| 하는 일 | 참가자끼리 서로를 가리킨다 | 그 sessionId의 주인임을 증명한다 |
| 유출되면 | 아무 권한도 얻지 못한다 | 그 사람으로 재입장할 수 있다 |

### 방장 권한: 토큰이 있어야 한다

방장은 이제 `sessionId`가 같다는 이유만으로 되지 않습니다. 방장 역할은 **방장 토큰**(`hostToken`)을 가졌거나, 멤버 토큰으로 자기 `sessionId`의 주인임을 증명했을 때만 부여됩니다.

```js
const isOwner = typeof ownerToken === "string" && safeEqual(ownerToken, room.hostToken);
const memberValid = memberRecord && typeof memberToken === "string"
  && safeEqual(await sha256Hex(memberToken), memberRecord.tokenHash);
const role = isOwner || (memberValid && sessionId === room.hostSessionId) ? "host" : "member";
```

방장이 바뀔 때는 방장 토큰도 새로 발급해서(순환), 이전 방장의 토큰이 남아 있어도 쓸모가 없게 했습니다. 토큰 비교에는 시간 차이를 이용한 추측을 막는 `safeEqual`을 씁니다. 방장이 나가면 서버가 기록한 입장 시각으로 가장 먼저 들어온 참가자에게 승계하고, `joinedAt`은 더 이상 클라이언트에서 받지 않습니다.

### 강퇴: 진짜로 끊고, 다시 못 들어오게

강퇴하면 대상 소켓을 실제로 닫고, `ban:<sessionId>` 기록을 남겨 위의 WebSocket 검사에서 걸리게 했습니다. 방장이 승인해야 들어올 수 있는 **대기실**(승인 모드)도 함께 넣었습니다.

## 4. "서버는 안 본다"는 약속과 동작을 맞추다

점검에서는 구멍 말고도 **약속과 실제가 다른 곳**이 나왔습니다. 이 앱의 소개는 "팀 자료는 서버에 남지 않는다"였는데,

- 직접 연결(WebRTC)이 열리지 않은 상대에게는 앱 내용 전체를 서버를 거쳐 중계하고 있었습니다(TURN 서버가 없고 STUN만 있었습니다).
- 브레인스토밍의 "공개 전까지 비공개" 아이디어가 실제로는 **본문과 작성자까지 모두에게 전송**되고, 화면에서만 가려져 있었습니다. 개발자 도구를 열면 보였습니다.

고친 방식은 이렇습니다.

- 서버 중계는 **제어 메시지 몇 가지만** 허용하고 16KB로 제한합니다. 코드에 "앱 내용은 이 경로를 쓰지 않는다"고 적어 두었습니다.
  ```js
  // Control-message fallback while DataChannels are opening. App content never uses this path.
  case "relay-app": {
    if (raw.length > RELAY_MAX_BYTES) return;   // 16KB
    // ...
  ```
- 블라인드 모드에서는 아이디어를 **봉인된 카드**(`{ id, createdAt }`)로만 전송합니다. 본문과 작성자는 작성자 자기 기기에만 남고, 방장이 공개하면 각 작성자가 자기 글을 직접 게시합니다. 대가도 있습니다. 작성자가 공개 전에 방을 나가면 그 카드는 영영 열 수 없고, 화면에도 그렇다고 표시합니다.
- **TURN은 쓰지 않기로 했습니다.** 과금 때문입니다. 대신 직접 연결에 실패하면 원인과 해결 방법을 안내하는 화면을 넣었습니다.

## 5. 서버를 속이지 못해도, 상대 브라우저는 속일 수 있다

서버 권한을 정리하고 나니 반대편이 보였습니다. 참가자끼리 직접 주고받는 P2P 메시지에서는 서버가 중간에 없으므로, **"방장이 보낸 것"이라는 주장을 서버가 보증할 수 없습니다.** 퀴즈 정답 공개나 투표 마감 같은 방장 전용 동작을 다른 참가자가 P2P로 흉내 낼 수 있었습니다.

그래서 브레인스토밍, Q&A, 투표, 퀴즈에서는 **방장 전용 동작을 받는 쪽이 발신자의 역할을 확인**하게 했고, 투표는 메시지에 적힌 이름이 아니라 **실제 발신자** 기준으로 기록합니다. 그리고 아직 남은 약점도 문서에 적어 두었습니다. 늦게 들어온 사람에게 현재 상태를 보내는 동기화 메시지(`poll:sync-state` 등)는 아직 누구나 보낼 수 있습니다.

## 6. 고친 뒤에 확인한 것

- 단위 테스트 7개 파일(입장, 방장 승계 규칙 등)이 통과했습니다. 방장 승계는 최근 3개 커밋에서 연달아 고쳐진 부분이었는데 테스트가 없었기 때문에, 서버 로직에서 순수 함수(`worker/policy.js`)를 떼어 내 테스트부터 만들었습니다.
- 실제 서버를 띄워 16개 시나리오를 시험했습니다. 입장권 없는/재사용한 WebSocket 거부, 비밀번호 401/403/429, 대기실 승인·거절, 멤버 토큰 재입장 등입니다.
- 실제 브라우저 2~3개로 대기실 승인 화면, 새로고침 후 복귀, 5MB 파일 전송을 확인했습니다.

계획에는 없었지만 시험하다 발견해 넣은 것도 있습니다. 첫 피어 연결이 실패 신호도 없이 멈추는 경우를 위한 12초 감시(watchdog), 접속자가 0명이면 누구나 같은 코드로 방을 새로 만들어 방장 토큰을 가져갈 수 있던 문제의 제한 등입니다.

## 정리

이 점검에서 가장 크게 남은 교훈은 세 가지입니다.

1. **테스트가 통과한다는 것은 안전하다는 뜻이 아니다.** 통과한 테스트는 테스트가 다루는 것만 보증합니다.
2. **공개되는 값을 신분증으로 쓰지 않는다.** 참가자끼리 서로를 가리키려고 모두에게 알리는 값(`sessionId`)은 이름표일 뿐이고, 권한은 서버만 아는 비밀(토큰)에서 나와야 합니다.
3. **소개 문구를 동작과 맞춘다.** "서버는 안 본다"라고 쓰려면 서버를 거치는 길이 어디인지, 그 길로 무엇이 지나가는지를 코드에서 확인해야 합니다.
