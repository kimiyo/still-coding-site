[가나 공방](https://study-hiragana.still-coding.cc/)은 히라가나와 가타카나를 펜으로 크게 따라 쓰며 익히는 학습 앱입니다. 글자를 쓰는 화면이 이 앱의 중심이라, 쓴 획이 화면에 남지 않으면 앱이 성립하지 않습니다.

그런데 iPad에서 Apple Pencil로 쓸 때 가끔 **획이 통째로 사라졌습니다.** 이 글은 그 버그를 추적한 기록입니다. 결론부터 말하면 앱 코드만의 문제가 아니었고, 그래서 완전히 고쳤다고 말할 수 없는 문제입니다.

## 1. 증상

| 현상 | 설명 |
| --- | --- |
| 둘째 획이 사라진다 | 한 획을 긋고 바로 다음 짧은 획이나 점을 찍으면, 약 3~5번에 한 번 그 획이 화면에 전혀 나타나지 않는다 |
| 긴 획은 괜찮다 | 한 번에 길게 이어 긋는 획은 문제없다 |
| 간격을 두면 줄어든다 | 획 사이에 1초 정도 쉬면 덜 나타난다 |
| 시리가 뜬다 | 짧은 입력을 반복하면 시리 요청 화면이 자주 나타나고, 그때 입력이 끊긴다 |
| PC에서는 안 된다 | 같은 코드가 마우스나 트랙패드로 쓸 때는 재현되지 않는다 |

가나 글자에는 짧은 선과 점이 많아서 긴 선을 긋는 일반 스케치 앱보다 이 문제가 훨씬 도드라졌습니다.

## 2. 먼저 앱 코드를 의심했다

PC에서 되는데 iPad에서만 안 된다고 해서 곧바로 iPad 탓을 하지는 않았습니다. 필기 캔버스(`InkCanvas`)의 포인터 처리에 그럴듯한 원인 후보가 여럿 있었습니다.

| 가설 | 내용 | 검증하고 알게 된 것 |
| --- | --- | --- |
| 활성 포인터 잠김 | `pointerup`이 오기 전에 다음 `pointerdown`이 오면 무시 | 고칠 가치는 있지만, 시리 화면이 뜨는 현상은 설명하지 못한다 |
| 같은 `pointerId` 재사용 | Apple Pencil이 획마다 같은 id를 쓰면 up과 다음 down의 순서가 꼬일 수 있다 | 실제로 대비해야 한다. 그러나 시리와는 별개의 축이다 |
| `setPointerCapture` 직후 `lostpointercapture` | iPad에서 캡처가 바로 풀려 획이 끊길 수 있다 | iPad 특화 문제일 수 있으나 시리와는 관계없다 |
| 손바닥 방지(palm guard) | 펜을 뗀 뒤 일정 시간 터치를 무시하면 연속 획을 삼킨다 | 제거해도 시리 문제는 남는다 |
| 포인터 다운 시 부모 `setState` | 연속 획 사이에 화면이 다시 그려지면서 리스너가 흔들린다 | 보조 요인 |

이 가설들은 하나씩 코드에 반영했지만, **증상의 핵심 — "짧은 입력이 반복될 때 시리가 뜨면서 획이 끊긴다" — 은 남았습니다.** 앱의 상태 버그라면 PC에서도 나와야 하고, 시리 화면이 뜨는 이유도 설명되어야 하는데 그렇지 못했습니다.

## 3. 가장 유력한 원인: 짧은 Pencil 입력을 운영체제가 제스처로 오인한다

증거를 모으면 이렇게 정리됩니다.

| 입력 | 운영체제·브라우저의 해석 경향 |
| --- | --- |
| 긴 연속 선 | 드래그·필기로 유지된다 |
| 짧은 선, 점, 빠른 연속 획 | 탭·더블 탭·짧은 스트로크에 가깝다 → 시스템 단축이나 시리 후보가 된다 |
| 획 사이가 충분히 길다 | 연속 제스처로 묶이지 않아 재현이 줄어든다 |

즉 짧고 빠른 Pencil 입력이 "필기"가 아니라 "명령"으로 해석되고, 그 과정에서 시리 같은 시스템 화면이 앞으로 나오면 웹 페이지가 포인터 입력을 놓칩니다(`pointercancel` 또는 입력 중단). 사용자에게는 "획이 안 그려졌다"로 보입니다.

이것은 **추론입니다.** iPadOS 내부에서 실제로 무슨 일이 일어나는지 직접 관찰한 것이 아니라, PC에서 재현되지 않는다는 점, 긴 획과 짧은 획의 차이, 시리 화면이 뜨는 타이밍을 종합한 결론입니다.

## 4. 무엇을 했나

시스템이 하는 일을 웹 앱이 막을 수는 없으므로, **막을 수 있는 것을 모두 막고**, 앱이 스스로 입력을 삼키는 일을 없애는 쪽으로 갔습니다.

### 4-1. 필기 화면에서 브라우저 제스처를 끈다

```css
/* 필기 모드 전체 */
touch-action: none;
-webkit-touch-action: none;
```

원래는 `touch-action: manipulation`이었는데, 이 값은 더블 탭 확대 같은 것만 막고 짧은 탭성 입력의 여지를 남깁니다.

### 4-2. iOS 제스처 이벤트를 막는다

```ts
// InkCanvas.tsx — 핀치 등 페이지 제스처를 가능한 범위에서 차단
document.addEventListener("gesturestart", preventGesture, { passive: false, capture: true });
document.addEventListener("gesturechange", preventGesture, { passive: false, capture: true });
document.addEventListener("gestureend", preventGesture, { passive: false, capture: true });
```

`touchstart`와 `touchmove`에서도 `preventDefault()`를 호출합니다. WebKit이 터치 경로로 제스처를 먼저 판별하는 경우를 줄이기 위해서입니다.

### 4-3. 포인터 처리를 견고하게 만든다

```ts
// setPointerCapture / lostpointercapture 를 쓰지 않음
// 획 중에는 window 에 pointermove / pointerup / pointercancel 을 건다
// 같은 pointerId 로 다시 down 이 오면 이전 획을 닫고 새 획으로 처리한다
const beginStroke = (event: PointerEvent) => {
  if (activePointerRef.current !== null) {
    finishStroke(activePointerRef.current, activePointerTypeRef.current);
  }
  activePointerRef.current = event.pointerId;
  // ...
};
```

- 획 중에는 캔버스가 아니라 `window`에서 이벤트를 받아서, 빠른 업/다운이나 캔버스 밖으로 벗어난 입력에도 종료를 놓치지 않습니다.
- 부모 컴포넌트의 상태 변경(`onInkStart`)은 **획이 끝난 뒤 다음 프레임**에 호출합니다. 연속 획 사이에 화면이 다시 그려지지 않게 하기 위해서입니다.

```ts
window.requestAnimationFrame(() => {
  onInkStartRef.current?.();
});
```

## 5. 그래서 고쳐졌나

**완화했지만, 시리가 뜨는 것 자체는 웹에서 막을 수 없습니다.** `preventDefault`와 `touch-action`은 브라우저와 페이지의 제스처를 줄이는 도구일 뿐, 시스템이 처리하는 시리 진입이나 Pencil 하드웨어 단축(더블 탭, 스퀴즈)은 막지 못합니다. 그래서 문서에도 "완전 차단을 보장할 수 없다"고 적었고, 사용자가 확인할 설정(시리 및 검색, Apple Pencil의 단축, 손글씨 변환)을 함께 안내하도록 했습니다.

## 6. 다음에 비슷한 증상이 나면

이 프로젝트에서 정리해 둔 진단 순서입니다.

1. **PC에서 재현되는가?** 된다면 앱의 포인터 상태와 리렌더를 먼저 본다. 안 된다면 태블릿·모바일의 운영체제 제스처를 후보에 둔다.
2. **긴 획은 되고 짧은 획만 실패하는가?** 시스템이 탭이나 제스처로 오인하는 것이 강력한 후보다.
3. **실패한 순간에 시스템 UI(시리, 공유, 선택 메뉴)가 뜨는가?** 그렇다면 운영체제가 입력을 가로챈 것이다. 아니라면 캡처, 같은 `pointerId`, `setState` 타이밍, 캔버스 여러 개를 의심한다.
4. `touch-action`, `preventDefault`, `gesture*` 적용 여부를 확인한다.
5. 상태 변경이 `pointerdown` 직후에 있다면 획이 끝난 뒤로 옮긴다.

## 정리

이 버그에서 얻은 교훈은 하나입니다. **"내 코드의 버그"와 "환경의 간섭"은 증상 표에서 처음부터 나란히 놓아야 한다**는 것입니다. 앱 코드만 파고들었다면 시리 화면이 뜨는 이유를 끝내 설명하지 못했을 것입니다. 반대로 환경 탓만 했다면 실제로 있던 포인터 처리의 약점(캡처, id 재사용)을 고치지 못했을 것입니다. 그리고 웹이 막지 못하는 부분은 막을 수 없다고 인정하고, 사용자에게 알리는 쪽이 정직합니다.
