[가나 공방](https://study-hiragana.still-coding.cc/)은 설치해서 쓸 수 있는 웹 앱(PWA)입니다. 그래서 서비스 워커가 있습니다. 2026년 8월 5일, 새 버전을 배포한 직후 어떤 기기에서는 앱이 열리지 않았습니다. 콘솔에는 "JS/CSS의 MIME 타입이 맞지 않는다"는 오류가 떴습니다. 이 글은 그 문제를 **같은 날 두 번** 고친 기록입니다. 두 번째 수정에서 고친 것이 첫 번째 수정과 정반대 방향이었다는 점이 이 글의 핵심입니다.

## 1. 증상: 새로 배포하면 옛 사용자만 죽는다

증상은 이랬습니다.

- 배포 **직후**, 앱을 이미 써 본 브라우저에서만 화면이 뜨지 않는다.
- 콘솔에 스크립트나 스타일시트를 못 읽었다는 MIME 오류가 난다.
- 처음 방문하는 브라우저는 멀쩡하다.

"새로 방문한 사람은 되고, 이전에 방문한 사람은 안 된다"는 패턴은 캐시를 의심하게 합니다. 이 앱에서 캐시를 다루는 것은 서비스 워커(`public/sw.js`)뿐이었습니다.

## 2. 원인: 없는 파일에 HTML이 돌아오고, 그것이 저장된다

Vite로 빌드하면 스크립트와 스타일의 파일 이름에 해시가 붙습니다(`/assets/index-3f9a….js`). 새로 배포하면 해시가 바뀌고 옛 파일은 사라집니다. 여기에 두 가지가 겹쳤습니다.

1. **SPA 폴백.** 화면 이동이 주소가 아니라 앱 안에서 처리되는 SPA를 배포할 때는 "없는 주소는 `index.html`을 돌려준다"는 규칙을 흔히 둡니다. 그런데 이 규칙은 **없는 `/assets/…js`에도 HTML을 상태코드 200으로 돌려줍니다.** 브라우저는 JS를 기대했는데 HTML을 받으니 MIME 오류를 냅니다.
2. **서비스 워커가 그것을 저장.** 첫 버전의 서비스 워커는 "응답이 성공(`ok`)이면 무엇이든 캐시에 넣는" 방식이었습니다. 그러니 **HTML이 JS 주소의 캐시로 저장됩니다.** 이후에는 새로 배포해도 캐시가 먼저 답하므로, 고쳐진 서버를 두고도 계속 깨집니다. 코드 주석은 이것을 "캐시가 오염되었다(poisoned)"고 표현합니다.

처음 방문한 브라우저는 서비스 워커도 캐시도 없어서 깨끗한 새 파일만 받으니 멀쩡했던 것입니다.

## 3. 첫 번째 수정: 서비스 워커를 똑똑하게 만들다(오전)

첫 수정(`d915060`)은 서비스 워커의 방어를 늘리는 방향이었습니다.

- HTML 문서(화면 진입)는 **네트워크 우선**으로 바꿔서 새 빌드의 해시를 항상 받는다.
- 자산 주소에 HTML이 돌아오면 **캐시에 넣지 않는다**(`canCacheResponse`).
- `response.clone()`을 본문이 소비되기 전에 만든다(타이밍 버그 수정).
- `_redirects`에 `/assets/*  /404  404`를 추가해, 없는 해시 파일은 HTML이 아니라 404를 돌려주게 한다.

논리적으로는 충분해 보였습니다. 그런데 몇 시간 뒤에도 같은 오류가 다시 보고되었고, 같은 날 오후에 두 번째 수정(`ea0af05`)을 했습니다.

## 4. 두 번째 수정: 서비스 워커를 빼버리다(오후)

두 번째 수정의 커밋 메시지는 짧습니다. **"`/assets`는 서비스 워커가 손대지 않고, SPA 폴백은 없앤다."**

```js
// public/sw.js
function isBuildAsset(url) {
  // Vite hashed bundles — browser/CDN cache is enough; SW must not poison them with HTML.
  return url.pathname.startsWith("/assets/");
}

// Critical: do not intercept Vite build assets. A single bad HTML cache entry
// breaks the whole app with MIME type errors after deploys.
if (isBuildAsset(url)) {
  return;        // respondWith를 부르지 않으면 브라우저가 평소대로 처리한다
}
```

`fetch` 이벤트에서 `respondWith`를 부르지 않고 그냥 돌아오면, 그 요청은 서비스 워커가 없는 것처럼 브라우저가 알아서 처리합니다. 해시가 붙은 파일은 어차피 주소가 바뀌면 다른 파일이므로 **브라우저와 CDN의 캐시로 충분**합니다. 서비스 워커가 끼어서 얻는 이득은 거의 없는데, 잘못됐을 때의 피해는 앱 전체였습니다.

`_redirects`의 SPA 폴백도 아예 지웠습니다.

```text
# No SPA catch-all on purpose.
# This app uses in-memory screens (no path routes). A /* → index.html rewrite
# makes missing /assets/*.js|css return HTML (MIME type errors after deploys).
```

이 앱은 화면을 주소가 아니라 앱 안의 상태로 전환하므로 "없는 주소는 `index.html`"이라는 규칙이 필요 없었습니다. 필요 없는 규칙이 오류의 원인이 되고 있었던 것입니다.

## 5. 복구를 위한 장치들

원인을 고쳐도 **이미 오염된 브라우저**는 남습니다. 그래서 복구용 장치를 함께 넣었습니다.

- **캐시 이름을 올린다**(`kana-atelier-v5`). 서비스 워커가 활성화될 때 기존 캐시를 전부 지우고 다시 만듭니다.
- **서비스 워커 파일은 항상 네트워크에서** 받습니다(`/sw.js`는 캐시하지 않음). 그러지 않으면 고친 서비스 워커를 받지 못합니다.
- **등록 시 `updateViaCache: "none"`**, 그리고 탭이 다시 보일 때마다 `registration.update()`를 불러 새 서비스 워커를 빨리 집어냅니다.
- **새 서비스 워커가 제어권을 잡으면 한 번만 새로고침**합니다(`controllerchange`). 오염된 캐시를 쥔 채 화면을 이어 가지 않게 하려는 것입니다.
- 캐시에서 **HTML이 JS/CSS 자리에서 나오면 버립니다**(`cacheFirst`). 이미 오염된 항목을 만나면 지우고 네트워크로 갑니다.

```js
// 브라우저에 새 SW가 자리 잡으면 한 번만 새로고침
let refreshing = false;
navigator.serviceWorker.addEventListener("controllerchange", () => {
  if (refreshing) return;      // 무한 새로고침 방지
  refreshing = true;
  window.location.reload();
});
```

## 6. 지금의 캐시 규칙

| 요청 | 처리 | 이유 |
| --- | --- | --- |
| `/sw.js` | 항상 네트워크 | 서비스 워커의 업데이트가 캐시에 갇히지 않게 |
| `/assets/*` (빌드 산출물) | **서비스 워커가 개입하지 않음** | 잘못된 캐시가 앱 전체를 죽인다 |
| `/mnemonic/*`(연상 카드 그림) | 네트워크 우선, 오프라인이면 저장본 | 같은 주소로 그림이 교체될 수 있다 |
| `/info.css`, HTML 문서 | 네트워크 우선 | 새 빌드와 문서 변경을 바로 반영 |
| 그 밖의 정적 파일 | 캐시 우선 | 속도와 오프라인 |

## 7. 배운 것

- **캐시는 "성공한 응답이면 저장"으로는 안 된다.** 상태코드가 200이어도 내용이 기대한 종류가 아닐 수 있습니다. 저장하기 전에 무엇인지(`Content-Type`)를 봐야 합니다.
- **고치는 방향이 더할 것과 뺄 것 중 어느 쪽인지 따져 본다.** 첫 수정은 방어를 늘렸고, 두 번째 수정은 개입 자체를 없앴습니다. 이득이 거의 없는 곳(해시 파일)에서는 후자가 더 안전했습니다.
- **필요 없는 규칙을 의심한다.** SPA 폴백은 이 앱에 필요 없었습니다.
- **고친 뒤 복구도 설계한다.** 이미 망가진 브라우저가 스스로 낫게 만드는 장치(캐시 이름 변경, 한 번 새로고침)가 없으면, 수정은 신규 방문자에게만 효과가 있습니다.
