# 개발 노트 초안 검토 요청서

- 대상: `src/content/notes/` 아래 `draft: true` 초안 **24편** (공개 4편은 제외)
- 작성: Claude가 각 앱의 로컬 저장소 코드와 커밋 기록을 읽고 초안을 썼습니다.
- 목적: 사실 확인, 경험·의견 보충, 공개 여부 결정. 초안의 문장은 **출발점**이지 완성본이 아닙니다.

## 1. 검토자가 해야 할 일

각 글마다 아래 네 가지를 합니다.

1. **`<!-- TODO(사용자): … -->` 주석을 모두 처리한다.** 채우거나, 필요 없으면 지웁니다. 맨 위 "초안입니다" 주석도 지웁니다.
2. **사실과 다른 곳을 고친다.** 코드에서 읽은 내용은 근거가 있지만, 수치·날짜·동기·경험은 확인이 필요합니다.
3. **본인의 이야기를 넣는다.** 왜 만들었는지, 무엇이 막혔는지, 다시 만든다면 무엇을 바꾸겠는지는 코드에서 알 수 없습니다. 이것이 글을 남의 글과 구별하는 부분입니다.
4. **공개해도 되는지 판단한다.** 아직 고치지 않은 보안 약점, 개인정보, 비공개 예정 기능이 없어야 합니다.
5. **AI 말투를 지운다.** 초안은 AI가 썼으므로 문장 습관이 남아 있습니다. 기준과 프롬프트는 **6절**에 있습니다.

## 2. 확인 기준 (모든 글 공통)

| 항목 | 확인 내용 |
| --- | --- |
| 사실 | 코드 인용, 상수 값, 수치, 날짜가 지금 저장소와 일치하는가 |
| 추정 표시 | "~로 보입니다", "추정" 문장이 실제 이유로 바뀌었는가 |
| 번역 인용 | 커밋 메시지·주석을 번역해 인용한 곳이 원문과 뜻이 같은가 |
| 링크 | 앱 주소와 글 사이 링크(`/notes/…/`)가 맞는가. **초안끼리 건 링크는 대상이 공개돼야 살아납니다** |
| 보안 | 아직 고치지 않은 약점을 자세히 설명하지 않았는가 |
| 문체 | 본인의 말투와 맞는가. 과장·단정이 없는가 |
| 분량 | 실질적인 내용이 있는가. 얇은 글은 합치거나 보강한다 |

## 4. 공개 전 결정이 필요한 것

1. **Direct Play 보안.** 방장 판별이 세션 ID에 기대고, 방 접근 확인이 해당 방의 어떤 접근 토큰이든 받으며, 비밀번호 시도 횟수 제한이 없다는 점을 확인했습니다. 별도 작업으로 등록되어 있고 아직 시작하지 않았습니다. 이 점이 해결되기 전에는 `direct-play-spy-game-secrets`와 관련 글에서 **구조를 자세히 설명하지 않는 편이 안전**합니다. 방장 인증 글(DP-2)은 이 때문에 아직 쓰지 않았습니다.
2. **CollaBoard.** 같은 종류의 문제를 이미 고쳤다고 글에 적었습니다. 고친 코드가 운영에 나가 있는지 확인한 뒤 공개하세요.
3. **발행일.** 초안의 `pubDate`는 2026-10-01~10-04입니다. 실제 공개일로 바꾸세요. 목록은 이 날짜 순으로 정렬됩니다.
4. **편수.** AdSense 심사용으로 15~20편이 필요하다는 판단이면, 위 A·B 중 근거가 탄탄한 글을 먼저 공개하는 순서를 권합니다.

## 5. 검토를 마친 글을 공개하는 방법

한 편씩 아래 순서로 합니다.

1. 본문의 `TODO(사용자)` 주석을 모두 처리하고 맨 위 "초안입니다" 주석을 삭제합니다.
2. frontmatter에서 `draft: true` 줄을 삭제합니다.
3. `pubDate`를 공개일로 고칩니다. 내용을 크게 고쳤다면 `updatedDate`를 씁니다.
4. `pnpm run build`를 실행합니다. TODO가 남았거나 폴더와 `app` 값이 어긋나면 어느 글인지 알려 주며 실패합니다.
5. 커밋하고 `pnpm run deploy`로 배포합니다.

남은 TODO 수 확인:

```bash
grep -rc "TODO(사용자)" src/content/notes
```

`astro dev`로 열면 초안이 "초안" 배지와 함께 보이므로, 브라우저에서 실제 모양을 보면서 고칠 수 있습니다.

## 6. AI 느낌 지우기 요구사항

이 초안들은 AI가 썼습니다. 사실은 코드에서 뽑았지만 문장에는 AI 특유의 습관이 남아 있습니다. AdSense 심사와 독자 모두에게 "본인이 겪은 이야기"로 읽혀야 하므로, 공개 전에 아래 기준으로 고칩니다.

**원칙: 다른 AI에게 "자연스럽게 고쳐 줘"라고만 맡기면 또 다른 AI 말투가 됩니다.** 금지어, 문장 구조 규칙, 어조를 구체적으로 정해야 합니다. 그리고 가장 좋은 방법은 AI가 다듬기 전에 **본인의 경험과 판단을 먼저 넣는 것**입니다. AI는 없는 경험을 지어낼 수 있으니, 다듬기는 본인 내용을 넣은 뒤에 합니다.

### 6.1 이 초안들에서 자주 보이는 AI 습관

검토할 때 아래 패턴을 찾아 고칩니다.

| 패턴 | 예 | 고치는 방향 |
| --- | --- | --- |
| 균일한 글 구조 | 모든 글이 "문제 → 원인 → 해결 → 한계 → 정리" 순서에 번호 절 | 글마다 흐름을 다르게. 절 수를 줄이고 이야기 순서로 |
| 교훈형 결말 | "~는 신호였습니다", "핵심은 ~였습니다" 식 "정리" 절 | 마지막 절을 지우거나 사실 한두 문장으로 끝낸다 |
| 강조 문장 | "이것이 이 글의 핵심입니다", "가장 중요한 부분입니다" | 삭제. 중요하면 내용으로 보인다 |
| 대구·반복 구조 | "A가 아니라 B였습니다", "느린 것이 아니라 못 찾는 것" | 한두 번만 남기고 평서문으로 |
| 완곡·추측 | "~로 보입니다", "~한 것으로 추정됩니다" | 본인이 아는 사실이면 단정. 모르면 TODO로 확인 후 삭제 |
| 접속사·전환어 | "또한", "한편", "다만", "즉" 남용 | 대부분 삭제 |
| 과한 서식 | 굵은 글씨, 표, 목록이 문단마다 | 표는 비교가 꼭 필요한 곳만. 굵게는 문단당 한 번 이하 |
| 말줄임 없는 문어체 | 모든 문장이 "~입니다"로 끝남 | 본인 말투로. "~했다/~더라" 등 섞어도 된다 |
| 가짜 구체성 | "실측", "측정해 보니" 뒤에 본인이 안 잰 숫자 | 본인이 잰 것인지 확인. 코드 주석의 수치는 **출처를 밝힌다** |
| 없는 경험 | "처음 구현해 보니", "시연해 보니" | 본인이 겪은 일만 남긴다 |

### 6.2 금지 표현 (검색해서 지운다)

`또한`, `뿐만 아니라`, `한편`, `결론적으로`, `요약하자면`, `살펴보았습니다`, `살펴보겠습니다`, `시사하는 바가 큽니다`, `중요한 시점입니다`, `기대해 봅니다`, `도움이 되길 바랍니다`, `핵심은`, `가장 중요한`, `~라고 할 수 있습니다`, `~해 볼 수 있습니다`, `다양한 측면`, `이를 통해`, `~에 주목할 만합니다`

검색 예:

```bash
grep -rnE "또한|뿐만 아니라|결론적으로|요약하자면|살펴보|시사하는|핵심은|가장 중요한|할 수 있습니다" src/content/notes
```

### 6.3 지키면 안 되는 것 (AI에게 맡길 때도 유지)

- 코드 블록, 표의 수치, 상수, 파일 경로, 커밋 해시, 날짜는 **바꾸지 않는다.**
- 사실 주장을 새로 만들지 않는다. 모르는 것을 채우지 않는다.
- `TODO(사용자)`는 지우지 말고 그대로 둔다(본인이 직접 채운다).
- 본인이 쓰지 않은 경험담을 넣지 않는다.

### 6.4 퇴고용 프롬프트

아래를 복사해서 쓰고, 마지막 `[원문]`에 글 한 편(또는 한 절)을 붙입니다. **본인 경험을 넣은 뒤**에 쓰세요.

**A. 기본 (모든 글)**

```text
아래 글을 사람이 직접 쓴 것처럼 퇴고해 줘. 핵심 의미와 사실은 그대로 두고 다음 원칙을 지켜 줘.

[수정 원칙]
1. 접속사 최소화: '또한', '뿐만 아니라', '한편', '결론적으로' 같은 상투적 접속사는 삭제하거나 문맥으로 잇는다.
2. 문장 호흡: 길이가 비슷한 문장이 이어지지 않게 한다. 짧은 단문과 긴 문장을 섞는다.
3. 완곡·피동 금지: '~해 볼 수 있습니다', '~라고 할 수 있습니다' 대신 명확하게 말한다.
4. 교훈형 결말 금지: '정리' 절의 훈계조 마무리는 없애고 본문의 사실로 담백하게 끝낸다.
5. 강조 문장 삭제: '핵심은', '가장 중요한' 같은 표현을 쓰지 않는다.
6. 대구 구조('A가 아니라 B') 반복을 줄인다.
7. 평소 대화에서 쓰는 단어로 바꾼다.

[절대 바꾸지 말 것]
- 코드 블록, 표의 숫자, 상수, 경로, 커밋 해시, 날짜
- '<!-- TODO(사용자): ... -->' 주석
- 새로운 사실이나 경험을 지어내지 않는다.

[원문]
(여기에 붙여넣기)
```

**B. 개발 회고용 (경험담이 중심인 글)**

```text
아래 글은 개발 경험 글이야. 교과서 같은 설명을 걷어내고, 현업 개발자가 동료에게 자기가 겪은 일과 판단을 담백하게 이야기하는 톤으로 윤문해 줘.

- 장단점을 기계적으로 나열하지 말고, 필자가 내린 선택과 이유가 보이게 한다.
- '효율적으로 개선했다', '문제를 해결했다' 같은 추상적 서술은 무엇이 어떻게 바뀌었는지로 바꾼다.
- 정돈된 문어체보다 실무 회고에서 쓰는 실용적인 문장을 쓴다.
- 금지 단어: '요약하자면', '살펴보았습니다', '시사하는 바가 큽니다'.
- 코드, 수치, TODO 주석, 사실은 바꾸지 않는다. 없는 경험을 만들지 않는다.

[원문]
```
